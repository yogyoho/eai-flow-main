## 1. 本体方法论总纲

### 1.1 本体是什么

本体（Ontology）的工程定义（Gruber, 1993）：**概念化的显式规范说明**（an explicit specification of a conceptualization）。拆开说：

- **概念化**（conceptualization）：把某个领域"有哪些东西、它们之间有什么关系"抽象成一套共识模型——不关心具体数据，只关心**存在哪些类别的实体、什么关系是可能的、什么约束永远成立**。
- **显式**（explicit）：这些假设被写下来、机器可读，而不是埋在代码逻辑或人的脑子里。
- **共享**（隐含前提）：本体的价值在于让多个人/多个系统对同一套词汇达成一致——单人单系统用不着本体。

一句话：**本体是领域的"类型系统 + 关系词表 + 约束规则"，数据是它的实例。** 你们现有系统里，`doc_graph.yaml` 的对象类型/链接类型/枚举就是这个角色的轻量实现。

### 1.2 Gruber 设计五原则

1995 年 Gruber 提出的五条设计判据，至今仍是评审一个本体的第一道关卡：

| 原则 | 含义 | 对照本系统 |
|---|---|---|
| **清晰性** Clarity | 每个定义表达明确意图，不用私语 | `display_name`（中文）+ `description`（每对象必填，lint 检查空描述）✓ |
| **一致性** Coherence | 从定义推出的结论不能自相矛盾 | 跨域谓词门 + 谓词角色表（(org, project) 等）✓ |
| **可扩展性** Extendibility | 加新术语不改既有定义 | eia 域加入时 registry 仅扩 enum 两行、schemas 加域表三行——**验证成立**（EIA-T1/T2 实测）✓ |
| **最小编码承诺** Minimal encoding bias | 本体不应偏向某种具体实现编码 | ⚠️ 弱点：`etype`/`predicate` 是封闭 Literal 枚举而非开放类，语义上"承诺了实现"。有意的轻量化取舍（见 §4.4） |
| **最小本体承诺** Minimal ontological commitment | 只承诺建模所需的最小假设集 | ✓ 按域分 YAML、按需加谓词，从未试图一次建"企业全域本体" |

**审计结论**：五原则中四条已无意中达标；"最小编码承诺"的取舍（封闭枚举 vs 开放类）是有意识的架构决策，文档化于 §4.4。

### 1.3 本体工程生命周期（审计框架）

两个经典方法论给出生命周期的标准切分，本设计的 Gap 审计（§5）直接采用：

- **METHONTOLOGY**（Universidad Politécnica de Madrid, 1997）：规格说明 → **概念化** → 形式化 → 实现 → 维护。特点：首次把"概念化"（用非形式语言画清楚领域有什么）作为独立环节。
- **NeOn**（EU FP6, 2006-2008）：九个情景化场景，核心主张是**本体不是一次性建成而是与数据/应用协同演化**——"本体+数据+应用三轨并行"。

对照出的关键缺口预告（§5 详析）：**概念化环节在本系统完全缺位**——每次加域都是直接写 YAML（形式化+实现一步跳），没有一个"先用领域语言把实体/关系/约束说清楚"的中间产物。EIA 域导入是例外：sample_entities JSON + 大纲 digest 实际上扮演了概念化产物。

### 1.4 轻量本体谱系（定位你们的架构）

本体工程有一条"形式化程度光谱"：

```
重形式化 ←──────────────────────────────────────→ 重实用
OWL+DL推理机    RDF+SHACL    SQL语义层    Palantir Ontology    约定俗成词表
(W3C学院派)     (W3C工程派)   (数据团队)    (作战决策派)          (部落知识)
                                 ▲
                            本系统在此偏右
```

光谱没有对错，只有**与场景的匹配度**。你们的场景：Agent 推理 + 人工审核 + 千级实体 + 单团队治理——这个组合在光谱右半区是最优解（论证见 §3）。选轻量不等于不懂重的那端：§4 会把重端的每个标准讲清楚"它解决什么、我们为什么暂不需要、什么时候会需要"。

## 2. Palantir Ontology 解剖（对照本系统）

Palantir Foundry 的 Ontology 是当前企业本体工程化的最成熟商业实践——它回答的问题与你们完全同构："企业的数据怎么变成 Agent 和人都能操作的决策对象"。其体系四件套，逐件对照。

### 2.1 Object Types（对象类型）

**Palantir**：对象类型由数据集（dataset）支撑 + 属性映射 + 主键声明；对象是类型的实例，数据变更实时反映。
**本系统**：`ObjectType`（YAML registry）+ `uq_dg_entities_natural` 幂等 upsert + `graph_entity` 统一投影。

- **对齐度：高**。声明式类型定义、数据与类型分离、主键/游标语义一致。
- **缺口**：Palantir 的对象类型支持**多数据源拼接**（一个对象类型的属性来自多个 dataset join）——本系统一个 ObjectType 绑一个物理表（`access.table`），跨源属性需靠 Link 弥补。当前规模下取舍合理，记录在案。

### 2.2 Link Types（链接类型）

**Palantir**：链接由外键/连接器声明，基数（1:1/N:1/N:N）显式，支持链接上的属性（边属性）。
**本系统**：`LinkType`（source/target/cardinality/reverse/join 配置）+ `dg_relations` 边表（边自带 attrs/confidence/双时间）。

- **对齐度：高，且边属性能力反超**（Palantir 链接属性是后期特性；本系统边表原生带证据链 mention）。
- **缺口**：Palantir 链接类型在 UI 上可由分析师声明（schema-on-write 由平台保证）；本系统加链接类型 = 改 YAML+改代码，无声明式入口。**Gap：声明式 schema 管理入口**（低优先级，见 §5）。

### 2.3 Properties 与数据保护

**Palantir**：属性级权限（分类/标记驱动）、派生属性。
**本系统**：`hidden/filterable/searchable` 能力位 + 服务端投影强制 + 投影外列不可达。

- **对齐度：中**。能力位模型与 Palantir 属性分类同构；缺**派生属性**（由规则/函数计算的虚拟属性——§2.5 Functions 的下游）和**属性级访问控制**（当前是对象级 system:access 门禁，粗于 Palantir 的属性级标记）。列为 Gap。

### 2.4 Action Types（写回操作层）——**最大缺口**

**Palantir**：Action Type 是**对 Ontology 的一等写回操作**：声明参数、验证规则（含 Submission 级审批流）、执行的数据变更、以及操作后的副作用（通知/下游触发）。它是"人和 Agent 对业务系统做操作"的统一入口——点击按钮和 Agent 调 API 走同一个 Action。

**本系统现状**：写回能力散落在三处——(1) doc-graph 消解合并（REST+MCP 双通道，有留痕可撤销）；(2) ingest_extraction（实体写入）；(3) 规则派生（现算现返，刻意不落库）。

- **判定：消解合并就是一个特定的 Action Type**（参数=两实体 id，验证=自合并 CHECK+重复合并守卫，副作用=状态翻转+留痕），只是没有上升为**声明式的 Action 框架**。
- **Gap（v2.1 候选）**：把"带参数+验证+留痕+副作用"的模式抽象为声明式 Action 框架，消解合并/实体写入改造为其两个实例。**在此之前不要发明第二套写回**——每加一个写端点都按 Action Type 的形状写（参数声明/验证/留痕三件套），为将来框架化留好接缝。

### 2.5 Functions（计算逻辑层）

**Palantir**：Function 是类型化的纯计算逻辑（输入对象/属性→输出值/对象），可被 Action 引用作验证、可被权限控制、可版本化。

**本系统现状**：规则推理（`evaluate_rules`：YAML 规则→Rete 前向链→派生事实+触发轨迹）就是 Functions 的声明式子集——"从图谱事实计算新事实"。

- **判定：语义同构，形态不同**。Palantir 的 Function 是命令式代码（TypeScript），你们的规则是声明式 Datalog 式模式。声明式对本场景（合规可解释、非程序员可审）**更适合**，不是缺口。
- **真正的缺口**：规则只有 2 条演示规则——**函数层的丰富度取决于真实业务规则的出现**，这再次回到"真数据倒逼"原则。

### 2.6 语义动态（Live Ontology）

**Palantir**：Ontology 反映运营系统的实时状态（数据管道分钟级同步）。
**本系统**：registry/规则 SHA 指纹热重载 + 读侧实时投影（SQL 直查源表）。

- **对齐度：高**。你们的数据本就留在源表（本体是投影不是拷贝），实时性天然成立。EIA 域是例外（导入的静态知识快照）——已在 spec 中声明"样例参考知识"定位，一致。

### 2.7 Palantir 在你们规模上的不适用部分（诚实清单）

1. **对象级细粒度权限后端**（标记+属性级 ACL）——百人以下单团队，system:access+角色分配够用；触发重评条件：本体面向多租户/多客户交付时。
2. **生产级数据管道编排**（pipeline governance/血缘）——本系统本体是投影非数据仓库，血缘问题不存在。
3. **AIP 式的 Agent 应用商店**——你们自己就是 Agent Harness，这个角色由 harness 本体承担。

## 3. 语义层工程

### 3.1 数据网格方法论中的语义层

数据网格（Data Mesh）四原则（域所有权/数据即产品/自服务平台/联邦治理）中，与本模块直接相关的是后两条的结合：**语义层**是"把各域的产品化数据统一为一套可查询的业务词汇"的层。

判定语义层实现优劣的三条标准：

1. **真源不变**：语义层只读映射，不复制数据（消除双写一致性问题）；
2. **词汇收敛**：多源异名概念在语义层归一（消解/合并的角色）；
3. **消费接口统一**：人和机器用同一套词汇（SQL/REST/MCP 而非各自为政）。

### 3.2 本系统的合法性论证

| 语义层标准 | 本系统实现 | 判定 |
|---|---|---|
| 真源不变 | 本体 = 源表只读投影（v1 核心设计）| ✓ |
| 词汇收敛 | 消解流水线（norm 归一 + 0.92 审核带 + 合并留痕）| ✓ |
| 消费接口统一 | SQL（engine）+ REST（6+4 端点）+ MCP（5+1 工具）同一词汇表 | ✓ |
| 域所有权 | 按域分 YAML（bid/eia 各自文件）| ✓ |
| 治理 | fail-closed lint（枚举⊆、规则域归属、列声明⊆物理列）+ CI 集成 | ✓ |

**结论**：本系统是数据网格语义层的**轻量单域特化实现**，不是"还没上本体"的半成品。这个论证的意义：后续迭代（供应链/生产域）按同一模式加域 YAML 即可横向扩展，架构不需要重写。

### 3.3 约束层的 SHACL 概念对齐（决策：概念引入，不工程引入）

W3C SHACL 用声明式"形状"约束 RDF 数据（属性必须存在/取值范围/闭包语义）。本系统的约束机制逐条对齐：

| SHACL 概念 | 本系统对应物 |
|---|---|
| `sh:closed true`（闭包）| EntityPayload/RuleModel `extra="forbid"` + `_BUCKET_ETYPE` 五桶白名单（隐私结构性排除）|
| `sh:in`（值域枚举）| `etype`/`predicate` Literal 枚举 + registry yaml enum（双层，跨域谓词门）|
| `sh:minCount/sh:maxCount` | `entities min_length=1`、基数声明 |
| `sh:pattern` | `norm_name` 正则校验（归一化后比对）|
| SHACL 校验报告 | fail-closed `ValidationError/RulesError`（结构化错误）|
| 未对齐项 | 跨 etype 同名合并语义（"同名即同义"决策，收紧点已命名）|

**结论**：约束思维已等价实现且更贴工程栈；正式 SHACL 的重评触发条件 = 出现跨系统 RDF 数据交换契约（当前不存在）。已录入 §4.1 重评表。

## 4. 标准全景地图（附录性章节）

> 目的：把"对标准规范不清晰"转化为"知道地图上有什么、为什么当前不采纳、什么时候重评"。**每个条目都有明确的决策与触发条件**——这不是阅读清单，是决策存档。

### 4.1 W3C 语义网栈

| 标准 | 是什么 | 解决什么 | 当前决策 | 重评触发条件 |
|---|---|---|---|---|
| **RDF** | 三元组数据模型（S-P-O） | 异构数据统一表达；开放世界假设 | 不采纳：SQL 投影已表达同等语义，千级实体无互操作需求 | 跨组织数据交换契约；实体量达百万级且多源异构合并成本超阈值；或需对接标准数字化平台/交换标准本体数据时（GB/T 48000.3—2026，见 §4.4） |
| **OWL** | 本体语言（类/属性/公理/推理） | 形式化定义+DL 推理机自动分类 | 不采纳：Rete 前向链覆盖当前全部推理需求（5 条演示规则级）；OWL 的开放世界假设与业务系统的闭世界操作语义冲突 | 需要基于类层次/属性特性的自动分类（如"某设备属于某类则自动继承某约束"）且规则手写不可维护时 |
| **SHACL** | RDF 约束语言（闭世界校验） | 数据质量校验的声明式标准 | 概念引入（§3.3 对照表），不工程引入 | 同 RDF 触发条件；或多团队各自建域需要统一约束方言时；或需对接标准数字化平台/交付标准本体时（GB/T 48000.3—2026 已将 SHACL 列为该场景"应"条款，见 §4.4） |
| **SPARQL** | RDF 图查询语言 | 图模式的声明式查询 | 不采纳：engine 的 list/get_links/traverse 已覆盖查询模式；Ad-hoc 图查询由 Agent 的 MCP 工具组合承担 | Agent 频繁提出 SQL/Rete 均难表达的图模式查询（如变长路径+否定）时——当前 0 例 |
| **SKOS** | 词表/分类法模型（ broader/narrower） | 受控词表与术语间语义关系 | 不采纳：`etype` 枚举+归一化消解已覆盖当前词表需求 | 出现真正的同义词库/多语言术语对齐需求（如多语种环评术语库）时 |

### 4.3 决策记录

**2026-09-17 概念对齐路线（Q4-a）**：W3C 栈五件均"概念对齐、工程不采纳"。本决策的撤销成本评估：本体的显式声明特性（YAML/枚举/角色表）使未来任何一档的升级（导出/映射层/store）都是**增量翻译而非重构**——轻量路线的可撤销性正是选它的核心原因。

## 5. 本系统对照与 Gap 审计

> 双矩阵审计：矩阵 I 按 Palantir 四件套（能力维度），矩阵 II 按工程生命周期（流程维度）。每格：现状 → 缺口 → 裁决建议（✅接受现状 / 🔨补建 / 🤔架构裁决）。**本表为审计建议稿，最终裁决待用户确认（Phase A3）。**

### 5.1 矩阵 I：能力维度

| 能力 | 现状 | 缺口 | 裁决建议 |
|---|---|---|---|
| Objects/Links 类型系统 | registry+engine+地图全链 | ObjectType 绑单表（多源属性靠 Link）| ✅ 接受（记录于案） |
| Properties+数据保护 | 能力位+投影强制 | 属性级 ACL；派生属性 | ✅ 接受（触发条件已录 §2.3） |

## 6. 闭环路线图

### 6.1 Phase B 试点：投标资格预审推理（业务闭环验收）

**场景**：给定投标项目 → Agent 基于图谱回答"投标人是否持有该项目所需资质"→ 规则底座给出推理结论+证据链。

**数据准备**（Q14-c 混合路线）：bid 样例文件 LLM 抽取打底（顺带实战验收抽取闭环）→ 手工修 assure 置信度达标（≥0.7 进推理空间）→ 补齐 `bidder_holds_qualification` 关系密度。

**推理规则**（真业务规则，替换演示规则的时机）：

```yaml
# rules/bid.yaml（示意）
rules:
  - name: bidder_qualified_for_project
    when:
      - "bidder_of_project(?B, ?P)"
      - "bidder_holds_qualification(?B, ?Q)"
      - "project_requires_qualification(?P, ?Q)"
    derive: "bidder_qualified(?B, ?P)"
```

**验收判据**（Competency Questions——生命周期"规格说明"环节的落地示范）：
1. "横城煤矿项目的投标人是谁？"——图谱查询可答
2. "山西煤机集团持有什么资质？"——图谱查询可答
3. "哪些投标人具备项目所需全部资质？"——**规则推理可答**（这是本体存在的意义验证：无推理时此题需人肉比对）

**规模护栏**：资格预审规则是 join 型规则（非笛卡尔），触发预算充裕；若竞品样例扩充导致派生逼近 1000，按 bug-2188 的修复路径 #1（提高上限）处置。
