## Problem Statement

v3 压测闭环收口后，两个新事实浮出：

1. **篇幅现实与单文档架构冲突**：投标方案 Word 版普遍 300-1000 页（中文 19.5万-65万字），而当前交付形态是"商务卷.md + 技术卷.md"两个不分章的单文件（`build_output.py:842-843` 每卷单次 `render_volume_md` 调用）。经 8-agent 调研 + 对抗核验实证：
   - **对话页工件预览区**（.md 分支）：Streamdown/react-markdown 10 全文单棵 React 树渲染，无分页/虚拟化；1MiB Range 截断 + "加载全文"按钮（`loader.ts:39,66-71`），点全文即数 MB 主线程冻结；面板内编辑上限 2MiB 超出即 413（`artifacts.py:43,95-100`）；`refetchOnWindowFocus:true + staleTime:0`（`hooks.ts:46-48`）每次窗口聚焦全文重拉重渲。
   - **BlockNote 编辑器**（docmgr/collab，0.51.4）：全量加载模型无虚拟化（`PersonalBlockNoteEditor.tsx:872-902`、`BlockNoteEditor.tsx:686-719`），全量 md 同步解析+单事务 replaceBlocks 播种（`PersonalBlockNoteEditor.tsx:398-415`）；1.5s 防抖保存全文 `blocksToMarkdownLossy` 序列化（`PersonalBlockNoteEditor.tsx:424-531`）。**300 页（约 8k ProseMirror 节点，社区实测劣化阈值 5-8k 边缘）：能渲染但明显卡顿（首载 2-10s 阻塞、打字延迟几十-几百 ms）；1000 页（约 4.6 万节点，超阈值 6-10 倍）：不可用/极易假死 + OOM 风险**。协作路径 Hocuspocus 每 ~2s 全量 `encodeStateAsUpdate` 落库两份、collab_updates 无限增长（`collab-server/src/index.ts:105-109`、`persistence.ts:18-44`）。生产库实查：从未承载过 >57 页文档（最大 content 3.7 万字/74KB）。
2. **域规则修正（用户拍板）**：投标技术响应 = **逐项响应完备性 > 内容溯源性**——样例库仿写优先，样例库没有直接编造（合法且必要，空项=技术偏离=丢分）。v3 的三模式级联中 mode2（ask_clarification 要样例）/mode3（web_search）两条支路废弃。地质/环评类事实文书的"绝不编造"铁律**不可**移植到技术响应。

另有一个会话级事实：v3 实现主体曾被另一会话 stash（见 Constraints/已处置）。

## What Makes This Cool

标书是竞争文书不是事实文书——这个定位差异被显式化为生成政策（编造合法+四类硬围栏+全量人核清单），而不是靠提示词话术。同时把地质技能经过 64-agent 审计、T3/T4 页面实测打磨出来的机制做一次"反向移植"（geo v2 设计稿自己写明当年对标 bid 的机器层防护水平）——两个技能形成机制对流。

## Premises（用户已确认）

- **P1 编造政策**：技术响应逐项完备性优先；级联 = 样例库仿写 → 编造，不 ask_clarification 阻塞、不 web_search。
- **P2 编造边界**：叙述可编造 + 四类硬围栏——报价数字/资质证号/公司实体名/招标文件原文引用强制真实/逐字（错报价=废标，假资质=违法），走冻结数据/白名单管线。
- **P3 样例库底座**：RAGFlow 知识库（段落级仿写检索，filters 元数据过滤已支持）+ kf 结构模板（样例→模板抽取管线现成；kf 现无投标域，需新建）。
- **P4 人核策略**：编造段落全量进人核清单——复用 v3 `responses.json` 已有 `source_mode`/`needs_human_verify` 机制，语义从"如实标注降级"重定位为"批量确认清单"。
- **P5 大篇幅架构**：单文档不适合（300 页=体验红线，1000 页=不可用），选 **A 分册多文档**（每册 20-50 页，预览/BlockNote/协作/2MiB 编辑上限全部因文档变小而天然解决，且与标书分卷递交实践一致）。

## Approaches Considered（大篇幅架构，Phase 4 三选一）

- **A 分册多文档（选定）**：build_output 按章/册拆文件 + 总目录索引卷。Effort M+（human ~2-3 天 / CC ~1 天）；Risk 低-中。代价 = 册间目录/编号聚合与导出合并层（docmgr `generate_docx_simple` 多文档导出改造）。
- **B 单文档+只读分页预览**：服务端 md→HTML 分页预览，点编辑才进 BlockNote。Effort L；Risk 高——编辑路径打开时 BlockNote 仍全文加载，collab 写放大不解决，单独选等于只修一半。
- **C Yjs 多子文档**：Hocuspocus 官方 multi-subdocuments，每章一个 doc。Effort XL（协作粒度/权限重设计）；平台级最优但周期最长——适合作为 A 之后的演进方向而非前提。

排除逻辑：B/C 都是平台层补丁，A 是生成管线原生形态（structure.json 本就按章组织，geo 的 `state/chapters/chNN.md → build 组装` 模式已验证），A 落地后 B/C 的必要性大幅下降。

### WP-1 分册架构（核心，先做）

**0. 前置定案——两文档拓扑 + 切册规则（评审 C3 + eng-review 2A + 用户域规则 Revision 4）**：交付拓扑 = **整体投标方案 + 技术卷两文档**（招标一级大纲中技术仅占一章、其余全商务；技术标单独装订/评标是行业实践）。**整体投标方案** = tender 镜像顺序连续渲染：商务章节实际内容（check_format 1:1 复刻纪律在此全文成立）；**技术章 = 占位页**——镜像章标题逐字 + 技术卷分册目录 + "详见《技术卷》"指引，**零内容内联**（判定机制现成：extract 已按节点标 `volume=technical`，顶级章子树全 technical 即占位；check_format 对该章断言降级为占位完整性：标题逐字+指针可解析+零正文泄漏）。**技术卷** = 自有大纲（招标只给一行，卷内结构来源级联 = 招标技术要求/评分办法条款聚类 → 样例库模板 → `origin=self_created` 节点，**门1 加技术卷大纲确认表**）。四类硬围栏域**不**集中成册；"集中"降级为索引卷/副表**汇总指针**。切册算法（贪心装箱）**同一套跑两棵树**：切满一册的判据 = 页数估算达到册上限（50 页，**软上限**）的章边界（标题深度 ≤3 的切点优先）；**单章自身超上限时整章成册 + 告警放行**（eng-review 2A：80 页册 ≈ 2100 块，远离 300 页 BlockNote 红线，不在章内硬切）。
