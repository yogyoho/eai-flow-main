## Problem Statement

OntoStudio（`ontostudio/`，FastAPI :8005 + Vite SPA）前端 9 页原型已建，但「人审抽取结果 → 确认入库」这条主路径断在最后一环：

1. **后端投影是假信号**：动作层（Tasks 1-10 已完成，基线 416）落库后 `_project_incrementally` → `get_kernel().refresh()` 只做 schema 重编+闭包+规则重跑，**从不读 `dg_*` 行**。确认后接口回 `projected: true, errors: []`，断言图里没有这一行（本机与活容器双向实测）。spec §2 步骤 5「提交后增量重投影」是全计划唯一未实装的管线步骤，已被 `tests/test_actions_e2e.py::test_03_action_projection_does_not_reach_the_graph_KNOWN_GAP` 钉住。
2. **前端没有动作调用 UI**：ResolutionPanel（547 行，已接 ontology-graph-api）能看待审结果，但没有确认/驳回按钮——动作层后端就绪，人却够不着。
3. 后果：人审是「审了个寂寞」——确认了但图不变，agent 查不到，闭环不存在。

## Demand Evidence

- **下线测试通过**：环评域是唯一真实数据全链路已验证的域（月儿湾报告：抽取 460 实体/205 关系 → infer 1857 物化 2.3s → covered_by_standard 9 条真实治理链 → validate 国标五项全过 → export 200）。
- 会话确认（D2）：环评域用户在行为上等待本体能力——抽取结果有地方沉淀、治理链能比对，是既有环评技能管线的延伸需求。
- 会话确认（D3）：**人在用前端但功能缺**——人审是设计的主路径（ResolutionPanel 已接真数据即为证），当前断层在动作 UI 与投影。

## Status Quo

环评域今天的使用方式：agent 经聊天 + MCP 13 工具查询本体；人偶尔打开前端看抽取/校验/推理结果（Modeler/Validation/Reasoning/Export 四页 + OntologyPage 全家桶已接真数据）。确认动作只能靠 REST/MCP 裸调 `actions/invoke`，且调用方拿到的是假 `projected: true`。EntitiesPage/IngestPage/CQ 验收单仍是「示例数据」水印静态页（`shared.tsx:99` 水印机制就是为此预留的）。

## Target User & Narrowest Wedge

- **目标用户**：环评域审阅者——逐条审阅抽取出的实体/治理链/阈值约束，确认后入库。
- **最小楔子**（D4 确认）：**确认 → 图真实更新 → agent 可查 → 下次抽取可比对**。每一环都已存在，只差投影实装 + 前端动作按钮。

## Constraints

- 所有对 ontostudio 的改动属 EAI-CUSTOM，须规范注释。
- ontostudio 无 Makefile：每个 Task 验证 = `ruff check` + `ruff format --check` 双检（主仓 make lint 是两条命令，只跑前者会漏）。
- `ontostudio-backend` 不 bind-mount 代码（compose 只挂 kernel 卷，镜像烘焙 `COPY app ./app`）——验证必须 `docker compose -p eai-docker -f docker-compose-dev.yaml build ontostudio-backend` 后 up，**restart 无效**。
- 动作层基线 416 测试不回退；KNOWN_GAP 测试实装投影后会转红，**届时删除它**（计划文档预留的机制）。
- 本切片不动 `roles_custom.yaml`（reviewer 授权是权限模块产品决策，列为后续批次）。

## Premises（D5 全部确认）

1. 前端「未实现」分两类：断在最后一环的人审闭环 vs 演示性静态页。只补第一类。
2. 投影实装（spec §2 步骤 5）是后端 P0：不修它，人审在任何 UI 下都是假的。
3. 前端不缺新页面，缺的是把已完成的动作层接到已有 ResolutionPanel 上。静态页无限期后置。
4. reviewer 角色授权是前置缺口（当前 `ontology:action:review` 只授 superadmin），但不搭车本切片。

## Approaches Considered

### Approach A: 最小闭环（同步投影简化版）— 已选定（D6）

Summary: `_project_incrementally` 实装为真增量投影（同步：动作事务提交后、响应返回前，把受影响行装进断言图；失败标 degraded + 错误明细）；ResolutionPanel 加确认/驳回按钮调 `actions/invoke`。
Effort: S-M（人工 ~3-4 天 / CC ~半天）｜ Risk: Low ｜ Completeness: 7/10
 Pros: diff 最小、每一环已存在；同步语义无队列无状态机；KNOWN_GAP 转红即删。
Cons: pyoxigraph 写锁在同步路径，确认请求被推理闭包（秒级）拖住；无 degraded 状态展示。

### Approach B: 投影状态机 — 一行否决

同步/异步裁决 + pending/projected/degraded 状态机 + 重投。Completeness 10/10 但工期 3 倍，多域并发收益当前吃不到——A 是其真子集，升级不浪费。

### Approach C: agent 预审分层 — 一行否决

置信度门预分、高置信自动确认、人只审低置信子集。踩在 A 之上且引入图污染信任风险，适合作 A 后第二批次。

## Recommended Approach

**A（最小闭环）**，实施顺序：

1. **投影实装**：`routers._project_incrementally` 调 kernel loader 的增量装载（受影响 IRI 集合 → 断言图），同步完成；失败返回 degraded + 错误明细。**同步订正 `_project_incrementally` 的 docstring**（现状只承认"非增量"，没承认根本没投影——计划文档点名此句也要修）。
2. **删 KNOWN_GAP 测试**：`test_03_action_projection_does_not_reach_the_graph_KNOWN_GAP` 实装后转红即删，改写为正测「确认后断言图含该 IRI 且 status=active」。
3. **前端动作 UI**：ResolutionPanel 待审条目加「确认/驳回」→ `POST /actions/invoke`（走 formal-api 或新建 actions-api 客户端）；按钮态区分投影成功（绿勾）/ degraded（黄警+错误明细）。
4. **验证路径**：容器 build（非 restart）→ 前端确认一条 → `GET /formal/export?graphs=asserted` 出现该 IRI 且 `status="active"` → agent MCP 查询可见。
5. **后续批次**（非本切片）：reviewer 授权（roles_custom.yaml overlay）→ 方案 C 预审分层 → 静态页接真数据（P2）。

## Open Questions

- 同步投影的确认请求耗时：infer 全量 2.3s，增量应远小于此——实测第一批确认的 P95 再定是否需要升级 B。
- `refresh()` 与增量装载的关系：增量装载后是否仍需全量 refresh（规则重跑），还是规则只对受影响 named graph 局部重跑——实现时实测裁决，倾向局部。
- 驳回动作的语义（软删/标记/回滚 mention）在 registry 动作声明里的现状——实现时核对 `registry/doc_graph.yaml` 的 actions 段。

## Success Criteria

1. 前端确认一条抽取结果后，`/formal/export?graphs=asserted` 含该实体 IRI 且 `status="active"`（KNOWN_GAP 场景反转）。
2. agent 经 MCP 能查询到刚确认的治理链/阈值。
3. 投影失败时前端显示 degraded + 错误明细，不再出现假 `projected: true`。
4. 全套回归绿（基线 416 + 新正测）。

## Dependencies

- 动作层 Tasks 1-10 已完成（`actions/executor.py` + `sql_write.py`，REST+MCP 已暴露）。
- kernel loader 增量装载能力（`kernel/loader.py::load_doc_graph_rows` 已有全量版，需确认增量入参）。
- reviewer 授权为后续批次前置（闭环第一版仅 superadmin 可审）。

## The Assignment

**下一步不是写代码。** 拿月儿湾报告的 460 条抽取结果，挑 5 条治理链，让环评域的**真实审阅者（不是你自己）**坐在屏幕前走一遍「看结果 → 确认 → 图里查到」，你在旁边不说话，记录他们哪一步卡住、哪一步问「这是什么」。ResolutionPanel 的信息架构是否匹配审阅者的心智模型，只有这个观察能回答——这比任何功能清单都值钱。

## What I noticed about how you think

- 你开场就把问题定性为「前端原型有了，但实际功能很多未实现」——一句话同时给出资产盘点和缺口定位，这说明你对系统状态有清醒的账本，不自我安慰。
- D3 你选了「人在用前端但功能缺」而不是「主要走 agent/MCP」——尽管 MCP-first 是这套系统的设计出身，你没有为架构立场辩护，而是承认了真实工作面在前端。按证据站队而不是按立场站队，这是对的。
- D5 你对「reviewer 授权不搭车」没有犹豫——你清楚权限是另一个模块的产品决策，搭车会把一个 S-M 切片拖成跨模块谈判。知道边界在哪和知道该做什么一样重要。
