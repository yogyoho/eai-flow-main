## Problem Statement（问题陈述）

水泥厂厂长每月拿到能耗报表："本月熟料热耗 3520 kJ/kg，超标 80。" 报表只告诉**结果**，不告诉**为什么**、**亏了多少钱**、**该找谁**。厂长面对一个经营黑盒：
- 超标亏了多少真金白银？（3520 vs 对标 3440，× 月产 8 万吨 × 标煤价 → 一笔可算的损失，但今天没人算给他看）
- 是哪条产线、哪个班次、哪个煤种供应商、哪次工况事件拉高的？（归因到责任单元，厂长才能考核/换煤/调班，而不只是让工艺员去调阀门）
- 趋势是在恶化还是好转？对标行业/设计值差距多少？

**「智能问数」要解决的不是"操作员看不到测点"，而是"厂长看不见损失与责任"。** 把 DCS 里操作员级别的实时数据，翻译成厂长级别的**经营根因**：损失量化 + 责任归因 + 趋势对标。

楔子：**能耗（热耗/电耗）超标的经营根因分析**（厂长买单理由 = 直接可量化的成本损失）。

厂长问能耗，**两种时间尺度都要答**——缺一不可：
- **月度对标**：「这个月 2 号窑热耗为什么比上月高 50 kJ/kg、亏了多少」——经营复盘。
- **日度环比**：「为什么今天的电耗比昨天高」——**高频日常**，厂长几乎每天问，且昨天→今天还来得及当场纠偏。电耗按各大电机分解（功率×时长/产量）特别干净，是日环比里 AI 归因最 tractable 的——**作为 MVP 的日常高频靶子**。

## Demand Evidence（需求证据）

- 场景为**真实水泥厂**，DCS 实时数据困在厂内 DCS/HMI（和利时 / 浙大中控 / 西门子 PCS7 之一），尚无统一查询/经营分析入口。
- **买单人 = 厂长**：水泥能源成本占生产成本 60%+。热耗每降 10 kJ/kg，万吨熟料省煤折标数吨——直接进利润。厂长为**钱**买单，不为操作便利买单。
- **关键洞察**：操作员今天已经"看得到"测点（在 DCS HMI 里），痛点不在可见性；厂长的痛点是**数据没被翻译成经营语言（钱/责任/趋势）**。这是 AI + 因果图能拉开差距的地方，也是 v1（操作员视角）没对准的靶心。
- ⚠️ 头号风险仍是**数据可读性**（OPC UA 能否从该厂 DCS 取数）未验证——本设计前置闸门（见 Premises #1、The Assignment）。

## Status Quo（现状：厂长今天看见什么）

厂长层的能耗管理现状：
1. **能耗日报/月报只给结果**：热耗/电耗数值 + 是否超标，**没有根因、没有损失金额、没有责任归因**。
2. **责任无法穿透**：超标了，但不知道是甲班还是乙班、是 1 号窑还是 2 号窑、是这批煤热值低还是操作失误——厂长只能笼统追问工艺车间，车间再回去翻 HMI。
3. **损失没人量化**：超标 80 kJ/kg 到底等于多少钱，没人按月算给厂长；经营会上能耗是个模糊的"高了"，不是一笔账。
4. **对标缺失**：和设计值/历史最优/行业标杆的差距没有持续跟踪，改进无从闭环。
5. **数据分层断裂**：DCS（实时工艺）+ LIMS（煤质/熟料化验，日级）+ EMS（电度/煤耗台账）+ 财务（煤价）四套数据，没有任何一层把它们拼成"厂长的一笔账"。

**对比操作员层**：操作员在 HMI 里能看测点、能翻曲线、能凭经验判断哪个偏离——操作员的痛点是"慢、靠师傅经验"，不是"看不见"。v1 设计瞄准的是操作员痛点；v2 瞄准厂长痛点——后者才是买单理由。

## Target User & Narrowest Wedge

- **主角 / 买单人**：**厂长**（及分管经营/生产的副厂长）。关心：损失金额、责任归因、趋势对标、可做经营决策（换煤种/考核班次/停线检修/投资改造）。
- **次角色 / 执行人**：中控操作员、工艺工程师。他们基于厂长视图的归因结果**下钻**到具体测点做工艺处置。
- **楔子**：能耗（**热耗 + 电耗并列一等**）超标的**经营根因**——纯能耗、为厂长优化。引擎做窑况/工艺多变量根因（因为窑况波动是热耗异常即时主因），但**输出一律量化到钱 + 归因到责任单元**。
- **两种查询模式**（都要支持）：①**对标超标 RCA**（是否超标+为什么+亏多少+找谁）②**日环比/同比差分解**（为什么今天比昨天高，差值分解到设备/班次/工况+折算元值）——后者是厂长日常高频问法。
- **未来扩展**：站稳后引擎换 domain pack 覆盖产量损失归因、质量（f-CaO）退货风险、非计划停机损失——全部"厂长的一笔账"模型。

## Constraints（平台铁律）

1. **3 层能力模型**：能力只能通过 MCP 工具 / Skill / 子 agent 到达 agent。智能问数 = `dcs_qa`(MCP 查询+量化) + `cement-energy-rca`(Skill 经营根因 SOP)。
2. **新独立模块**：全新 extension（新后端 + 新前端 + 新路由），**不动现有 `data_source/dashboard/project/approval/shell` 业务代码**。唯一触点：`shell/Sidebar.tsx` 加一行 nav。
3. **不动 harness 核心**。
4. **MCP 是唯一桥**：`dcs_qa/mcp.py` 独立进程，handler 内 lazy import app.*。
5. 时序样本+元数据落**独立 `postgres-dcs` 容器**（`timescale/timescaledb:pg16`，`DCS_DB_URL`），**不进 postgres-ext/agentflow**（blast radius 隔离，D1 决议）；中文注释；上游定制加 `EAI-CUSTOM`。
6. DB 迁移：`CREATE EXTENSION IF NOT EXISTS timescaledb` + `CREATE ... IF NOT EXISTS` / `ALTER ... ADD COLUMN IF NOT EXISTS`，写进 `dcs_qa/database.py::migrate_db()`，无 Alembic。
7. **内网离线部署**：水泥厂气隔离内网，组件全部可离线自托管（+1 timescale 镜像）。
8. Skill 禁 `allowed-tools`（bug-186 教训）。
9. **【v2 新增】损失量化是硬约束**：任何 RCA 输出必须含 ①损失金额（元）②责任归因（班次/产线/煤种/工况事件）③对标偏差。不量化的根因对厂长无价值。
10. **【REVIEW 新增】会计数据完整性**：①每个损失数字旁显式标注所用输入（煤价/对标/峰谷电价）+最近更新日期；②`LossEvent` 快照当时的 tariff/benchmark（tariff/对标改了，历史损失不变）。输入一过期，"损失 X 元"即精确的谎话——厂长看到第一个错数就不信这系统。

## Premises（前提，必须成立）

1. **【头号风险】数据可读性**：目标厂 DCS 能经 OPC UA（退而 OPC DA / 厂商 SDK）稳定暴露所需测点（煤量/煤热值/窑温/窑电流/风机电流/熟料温度/CO/预热器压差/台产/电度）。国产 DCS OPC UA 成熟度参差，**此条不成立则全案坍塌**。
2. **厂长经营数据可得**：除 DCS 工艺测点外，能拿到**标煤折算系数、煤价（或可配置）、各产线设计/历史对标热耗、班次/煤种台账**——否则"量化到钱 + 归因"无米下锅。这些多为低频人工/台账/财务数据，导入门槛远低于 DCS 实时取数。
3. **能耗根因可解释且可归因**：热耗/电耗主因能被「测点组合 + 水泥工艺因果图」覆盖，且能映射到责任单元（班次=时间、产线=空间、煤种=供应商、工况事件=操作）。
4. **时序体量可控**：单线 ~500–2000 测点 × 1Hz，TimescaleDB 连续聚合承接（2000×1Hz×30 天 ≈ 52 亿行 → 连续聚合 1m/1h 下采样后冷热分层）。
5. **执行顺序铁律**：最大风险在 L1（取数）+ L2-经营数据（台账/煤价），不在 AI 多聪明。先打通"从 DCS 读 1 测点 + 导入 1 条对标基线 → 算出 1 笔损失"。

## Approaches Considered（备选架构）

### Approach A: Agent 原生 + Timescale（独立容器）✅（选定）
- L1：cron-poll collector（asyncua OPC UA 读当前值，每 10-30s）→ **独立 `postgres-dcs` 容器**（`timescale/timescaledb:pg16`）的 TimescaleDB hypertable。
- L2：新 MCP server 暴露测点级工具 + **损失量化/归因工具**；agent 做"自然语言→选测点→算损失→归因"。
- L3：`cement-energy-rca` SKILL 承载水泥因果图 + 热耗/电耗计算式 + **经营根因 SOP（强制量化到钱+归因）**。
- 工作量 M / 风险中。复用 data_source MCP 模式（不碰其代码）、skill 系统、ABAC datascope。Timescale 用专用容器（blast radius 与 auth/knowledge/contract_price 的共享 DB 隔离）。

### Approach B: 独立时序服务 + 专用 NL2Query 语义层（理想长线）
- 独立 InfluxDB + 自研中文↔测点语义层 + 统计/LLM 混合根因。查询最确定，但多一个服务、多一整块自研、离线镜像更重。

### Approach C: 直连 Historian、不落地存储（横向验证）
- 不采集不建库，query_tags 走 OPC UA HDA 历史读。最小投入直击头号风险，但长期不可行——价值在作 A 的前置阅兵（Phase 0）。

## Recommended Approach（推荐与理由）

**Approach A**，按**风险倒序**执行（把 C 的"先验证读数"前置为 Phase 0 闸门）：
- 独立 timescale 容器（D1 决议）→ 与共享 extensions DB 隔离，blast radius 最小；离线 +1 镜像（timescale 离线友好）。
- Agent 原生 → 最少自研，贴合 DeerFlow。
- 复用 MCP 模式 + skill 系统 + ABAC datascope；ingestion = cron-poll collector（独立 compose 服务，复用 gateway 镜像，非订阅、不挂 gateway）。
- **不在未验证 L1 + 经营数据可得性的前提下先建上层。**

### 能力分层映射（3-Layer North Star 落点）— 用哪些原语

| 原语 | 用不用 | 理由 |
|---|---|---|
| **MCP 工具** | ✅ **核心** | 7 个只读工具（list_tags/query_tags/correlate/get_energy_kpis/quantify_loss/attribute_loss/explain_delta）= agent 触达 DCS 数据的**唯一通道**。无 MCP 则 agent 查不了数。这是主原语。 |
| **Skill** | ✅ **核心** | `cement-energy-rca` = 因果图 + 计算式 + 经营根因 SOP + 答案模板。告诉 agent **怎么用工具**产出厂长级答案。无 skill 则有工具无领域知识、会乱查。 |
| **子 agent** | ❌ **MVP 不上** | RCA 是聚焦的工具调用序列，lead agent + MCP + skill 在线程内即可完成。仅当 MVP 证明需分钟级深度调查（如全厂跨系统溯源）才考虑独立子 agent。 |

### 水泥能耗因果图（Skill 核心内容 + 责任归因挂载）

**熟料热耗 (kJ/kg clinker) = 净耗热 / 熟料产量**，诱因边（方向+符号+归因挂载）：
- 煤热值↓（煤种/供应商）→ 热耗↑ — **归因: 煤种**
- 煤水分↑ / 煤粉细度↑(粗) → 燃烧效率↓ → 热耗↑ — **归因: 煤制备工况**
- 窑尾温度↑ → 废气带走热↑ → 热耗↑ — **归因: 操作/工况**
- 熟料温度↑（冷却机效率↓/篦冷机料层异常）→ 熟料带走热↑ → 热耗↑ — **归因: 冷却机工况**
- CO↑ → 不完全燃烧 → 热耗↑ — **归因: 燃烧工况**
- 预热器漏风/压差异常 → 换热效率↓ → 热耗↑ — **归因: 设备/工况**
- **窑主机电流波动（窑况不稳/跑生料）→ 频繁调风调煤 → 多烧煤 → 热耗↑** — **归因: 班次操作** ← *即时主因，reframe 的桥梁*
- 生料 KH/SM 偏离 → 易烧性↓ → 需更高温度 → 热耗↑ — **归因: 生料配料**
- 环境温度↓（冬季）→ 系统散热↑ → 热耗↑ — **归因: 季节（非责任）**

**综合电耗 (kWh/t) = Σ(电机功率 × 运行时长) / 产量**，各大电机：生料磨/水泥磨主电机、高温风机/废气风机/尾排风机、窑传动。
**日环比↑ 的分解（`explain_delta` 归因轴）**：
- **台产↓**（产量少了）→ 单位电耗↑ — 归因: 工况/操作（最常见）
- **某电机功率↑**（电流升高：磨机堵磨/饱磨、风机挡板开度大、物料难磨）→ 归因: 设备工况
- **运行时长↑**（启停多/空载待机长/低产时段长）→ 归因: 生产调度
- **峰谷电价时段分布变化**（同样 kWh 移到峰段 → 元值放大）— 归因: 调度（厂长可改排产避峰，真金白银）

> 关键：电耗差既要分解到 **kWh 来源（哪台电机）**，也要折算到 **元（含峰谷电价）**——后者才是厂长的一笔账。

### 反方意见（最大风险不在清单内）
厂长价值完全取决于**会计输入数据（煤价/对标/班次/峰谷电价）准确且持续维护**。输入一过期，"损失 X 元"就是精确的谎话，厂长看到第一个错数就不信这系统。硬性补两条：
1. 每个损失数字旁显式标注所用输入 + 最近更新日期（透明）。
2. `LossEvent` 快照当时的 tariff/benchmark（tariff 改了，历史损失不变）。
