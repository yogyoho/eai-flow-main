## Problem Statement

装备制造类客户(投标方,对标 mock 库中的"东智装备制造"型主体)在工业招标中需要逐份编写投标方案。现状:投标负责人(老手)从旧标书复制打底,团队分章节各写各的,最后汇总对不齐;没人系统通读招标文件,评标要求靠口头转述,漏响应直接丢分甚至废标。客户明确向 EAI 提出需要 AI 辅助编写投标方案。

本 skill 把**招标文件**转化为**机器可核对的义务清单**(每条要求分类、锚定原文位置),并产出**统一的逐项响应骨架 + 偏离表**供团队分发填写——用确定性管线消灭"漏响应/对不齐/旧内容没改净"三类结构性风险。

## Demand Evidence

- **证据等级 A**:客户明确提过该需求(具体的人、有场景),非我方推断。
- **痛点全谱系**(客户侧自报):写得太慢、写得不好丢分、重复劳动、新人不会写——四条全中,根因是标书生产纯手工艺。
- **第一手观察**(会话持有者完整看过一次投标周期):
  - 大部分时间花在**找资料**(旧标书/资质扫描件/参数表),不是写;
  - 最后一夜在拼**格式**(目录/页码/签字/盖章/份数);
  - 招标文件**没人系统读**,评标项靠口头转述,漏响应;
  - 复制的旧内容带着**上一家的名字/旧参数**没改干净。
- **原话**(需求本质,两个独立模型均将其读成完整规格):
  > "商务和技术参数条款必须满足不能偏离,打分项尽可能地不丢分。"
- **结构补充原话**(用户 2026-08-16,定义产出形态):
  > "项目投标方案一般分为两个部分:商务部分和技术部分。商务部分严格参照招标文件要求章节结构、章节内容(填写的文字内容和表格格式、需要插入的图片);技术部分要最大限度满足招标文件中技术参数,支持用户手动上传补充样例方案、也可支持从知识库中查询。"
- **评分闭环原话**(用户 2026-08-16,追加 V1 硬需求):
  > "需要使用招标文件的评分标准对编写出来的投标方案进行模拟打分,给出改进和完善建议。"

## Status Quo

| 环节 | 现状 | 成本 |
|------|------|------|
| 打底 | 老手从旧标书复制改 | 老手时间 + 隐性知识单人依赖 |
| 分写 | 团队分章节,各写各的 | 口径不一,汇总对不齐 |
| 要求获取 | 口头转述招标文件 | 漏响应 = 丢分/废标 |
| 终稿 | 最后一夜拼格式 | 高强度熬夜,低级错误 |
| 替代方案 | 购买标书 SaaS(巧文书/快标书/标小信等) | 商业机密出内网 + 无自有投标数据联动 → 不可行 |

## Target User & Narrowest Wedge

- **主用户**:投标负责人/老手——方案写不出来/丢分时实际背锅的人。skill 定位 = 他的杠杆:AI 出统一骨架,团队填,他改终稿。
- **验收人**:市场部负责人(提需求者,KPI=中标率)。
- **最窄楔子(V1 只做这一件事)**:招标文件 → 结构化要求清单(区分 ★强制/评分/普通条款)→ **双部分产出**——商务部(严格镜像招标文件章节结构的填空骨架)+ 技术部(技术参数逐项响应骨架,证据来自上传样例方案)+ 偏离表 → **模拟评分闭环**:按评分标准对当前成稿逐项模拟打分,输出失分点+改进建议(会话内更新的填写态随时可重跑;团队在 Word 里填完回传的成稿,需先经阶段5 的确定性重灌把状态对齐再评分——见阶段5)。整篇生成、资产库、情报注入全部后置。

### 产出形态:商务 / 技术 双轨(用户结构补充的落地)

| | 商务部分 | 技术部分 |
|---|---|---|
| 结构来源 | **严格镜像招标文件要求的章节结构**(常在"投标文件格式"章节),不自创结构 | 格式章节**若规定了技术部结构,同样优先镜像**;未规定处才按技术参数条款逐项组织(清单驱动兜底) |
| 槽位类型 | 类型化槽位:文字槽 / 表格槽(复刻要求的表格格式)/ 图片槽(需插入的证件/图纸扫描件) | 参数响应条目:要求原文锚点 → 响应要点 → 证据引用 → 满足状态 |
| 填充逻辑 | 按招标文件规定内容填空;格式即合规,不满足=形式评审扣分/废标 | 最大限度满足技术参数;每条参数必须应答,应答不了进偏离表 |
| 证据源 | 资质证书/营业执照等扫描件(用户提供) | ①手动上传样例方案(线程附件+沙箱全文检索)②知识库(见可达性说明) |

## Constraints

1. EAI 三原语模型:能力只能经 MCP/Skills/sub-agents 到达 Agent;V1 形态 = skill(`skills/public/<name>/` + `extensions_config.json` 注册),不做独立前端。
2. 私有化红线:招标文件与标书不出内网;解析全部走本地/已部署服务(eai-flow-ocr)。
3. 废标风险红线(移植 water-drainage 铁律):无出处的值标 `[待确认]`,绝不编造;每条提取项必须带原文位置锚点。
4. 沙箱依赖:config.yaml 选定 LocalSandboxProvider(本地模式),脚本实际跑 gateway venv——pdfplumber 0.11.9 已随 markitdown 在该环境(ocr-service 亦在用),import 即可用,仍需一次实测;python-docx 同环境在用(markdown-to-docx 先例),但按 fire-protection 技能的教训,ingest 需带 zipfile+XML 直读兜底路径。若部署切到 AIO/k8s 沙箱需重新核实(见 Open Questions 3)。
5. 现有 bid-quote 数据仍为 mock;真实投标库接入前,数据联动类能力只做接口预留。

## Premises

1. 自建而非买 SaaS 成立:私有化 + bid-quote 历史数据联动 + 平台已部署。若 SaaS 满足 80% 需求,项目应重评。
2. 主用户=投标负责人(老手);skill=他的杠杆,不是替代,不是新人填空玩具。
3. V1 只做楔子 A:要求清单 + 双部响应骨架 + 偏离表 + **模拟评分与改进建议闭环**(用户 2026-08-16 追加,对应原话"打分项尽可能地不丢分"的仪器化)。整篇生成/资产库/情报注入后置。
4. 每条提取项带原文锚点(页码/章节号)供人工核对;强制条款响应值无出处即标 `[待确认]`,绝不编造。
5. 招标文件 Word/PDF/扫描件混杂。docx/有文本层 PDF 走本地解析;扫描件依赖 eai-flow-ocr——注意现有 `/ocr` 端点只返回表格抽取+前几页文本,**全文 prose OCR 需在服务侧新增模式/端点**(V1 把它列为受限支持并挂 Open Question);必须支持答疑/补遗文件增量合并(隐藏废标项主藏身处)。
6. **(二次修订:codex 挑战后用户裁决搭便车;用户 2026-08-16 补充双证据源)** 结构化资产库二期;V1 技术部填充 = 手动上传样例方案(线程附件+sandbox 全文检索,不建持久库)+ 知识库查询(仅 knowledge-factory MCP 已可达——但其语料是环评/水保/消防类报告模板,是否含投标类模板未验证,V1 价值可能接近零,如实标注;RAGFlow 语料检索因无 MCP 接线不承诺,见 Open Questions 9)。
7. 双形态输出:结构化数据(JSON/表格,可核对)+ Word 文档(走 markdown-to-docx / output 扩展链路)。
8. 交付形态 = skill 挂对话 Agent,V1 无独立前端。

## Cross-Model Perspective

Codex(deepseek-v4-flash)冷读,全文要点:

- **Steelman**:真正的产品是"招标义务契约"——每条要求成为机器可核对项,分门槛(零偏差)/得分(不丢分)/中性三类,各带可引用出处,团队响应全部可追溯到清单并自动生成偏离审计。Word 骨架只是交付载体;**结构化义务模型才是产品**,二期资产、整篇生成、评分预测都插在它上面。
- **关键洞察**:那句"商务和技术参数条款必须满足不能偏离,打分项尽可能地不丢分"就是全部规格——两类约束、两种失败模式(废标 vs 静默丢分),并直接定义了成功指标:**强制条款零漏检 + 打分项最大找回,而不是文采**。
- **挑战前提**:P6(资产库二期)与 Q5(a)(时间在找不在写)矛盾;纯清单不解决最大时间成本。→ 用户裁决采纳修订版(搭便车检索)。
- **48h 原型**:LangGraph skill + 确定性管线(python-docx/pdfplumber/OCR 分流 → 严格 JSON schema 提取 → 确定性溯源校验 → 按 clause_id 合并补遗 → 清单+偏离表 → md-to-docx);验收=真实招标文件 vs 老手手工清单的召回对比;跳过资产库/检索/整篇生成/排版/前端。

## Approaches Considered

### Approach A: 纯轻技能(只写 SKILL.md)
零新代码,Agent 用已有能力在对话内解析+提取+出骨架。Effort S(CC~1天),Risk High:百页招标文件打爆上下文;JSON 结构靠 prompt 软约束必漂移;补遗合并/阶段确认全靠模型自觉——water-drainage 的实证教训(agent 自写整篇生成器)会复发。

### Approach B: 技能 + 确定性脚本管线(water-drainage 模式)✅
SKILL.md + scripts/(解析 ingest / 分块准备+校验 extract / 合并 merge_addenda / 产出 build_output / 评分模拟 score_simulate 五个脚本——前四个确定性,第五个=确定性骨架+Agent 评审循环)+ references/(schema/分类规则/评分规则/prompt 模板)。Agent 负责编排 + 在上下文内跑 LLM 提取/评审循环(脚本不做 LLM 调用——仓库虽有脚本侧凭证先例({image,video}-generation 调模型 API + required-secrets frontmatter),但本 skill 无需它:Agent 驱动的循环更可审计、可中断),每阶段产 artifacts,多轮确认门。Effort M(CC~4-6天),Risk Low:本仓库已验证的模式;codex 48h 原型即此路线。

### Approach C: 后端扩展 + MCP 工具(服务化义务清单)
仿 contract_price 新扩展模块:parse_tender/merge_addendum/build_skeleton MCP 工具 + 条款清单入库版本化。Effort L(CC~1-2周),Risk Med:清单成持久企业资产、二期插座天然,但楔子未经验证先付扩展+DB+注册+维护全额税。

## Recommended Approach

**B(脚本管线)**。楔子的命门是提取召回率与可审计性——这要确定性代码而非 prompt 自觉;C 的持久化收益要等清单数据模型被一次真实投标验证后才兑现。B 的 JSON 契约稳定后,二期原样升舱进 MCP(脚本被服务吸收,契约不变)。

### 详细设计

**技能名**:`bid-proposal-writing`(投标方案编写)

**目录结构**(仿 water-drainage-report):
```
skills/public/bid-proposal-writing/
├── SKILL.md                  # 触发词/铁律/阶段编排/确认门
├── scripts/
│   ├── ingest.py             # 输入分流解析(N 份基础文件) → sections.json(每节带锚点);
│   │                         # 纯结构化:章节树/锚点/格式章节定位,不做语义判断;
│   │                         # python-docx 失效时 zipfile+XML 直读兜底(fire-protection 先例)
│   ├── extract.py            # 分块准备(chunk 提示词组装)+ 候选结果确定性校验/去重;
│   │                         # LLM 提取循环由 Agent 在上下文内执行(见阶段2,仓库先例如此)
│   ├── merge_addenda.py      # 补遗/答疑增量合并:消费 Agent 已产出的候选映射与用户裁决,
│   │                         # 确定性落账;内容哈希台账保证幂等(重复合并跳过)
│   ├── build_output.py       # 清单+双部骨架+偏离表+覆盖率报表+实体一致性lint → markdown
│   └── score_simulate.py     # rubric.json 校验(含 Σmax_score 与评分办法总分一致性)
│                             # + 回传稿锚点重灌 + 客观分汇总 + 评分模拟报告渲染;
│                             # 主观项 LLM 评审循环由 Agent 执行(同阶段2 模式)
└── references/
    ├── clause_schema.json    # 条款 JSON Schema(见下)
    ├── structure_schema.json # structure.json 节点 Schema(槽位类型/枚举)
    ├── rubric_schema.json    # rubric.json 项 Schema(含 score_type 枚举)
    ├── classification.md     # 条款分类规则(★强制/评分/普通 判据+边界案例)
    ├── extraction_prompt.md  # 提取 prompt 模板(每块一次,强 schema);含三个子模板:
    │                         # 条款提取 / 结构槽位定型 / 评分细则→rubric 抽取
    └── scoring_prompt.md     # 模拟评分 prompt 模板(逐 rubric 项:证据引用+给分理由+失分点)
```

**核心数据模型 — 义务清单(obligation inventory)**,`clauses.json` 每项:
```json
{
  "clause_id": "ZB-C-017",        // 复合 ID:<文件代号>-C-<全局序号>(ZB=招标文件/JS=技术规范书/
                                  // PB=评分办法…),防跨卷撞号;顺序分配、类别无关(class 可人工改,ID 不变)
  "source_file": "招标文件.docx",
  "class": "mandatory",           // mandatory(★强制,零偏离) | scoring(打分) | normal
  "category": "technical",        // technical | commercial | qualification | format | service
  "source_ref": {"page": 23, "section": "3.2.1", "para": 14, "quote": "原文片段(≤50字)"},
                                  // page 按来源可空:docx 无分页概念→用 section+para(段落序)锚定;
                                  // PDF/OCR 扫描件才有 page
  "requirement": "要求内容(结构化转写)",
  "response_status": "unassigned",// unassigned | draft | pending_confirm | compliant | deviation
                                  // (中文仅为显示标签:未分配/草稿/待确认/应标/偏离)
  "response_skeleton": {"points": ["…"], "evidence_ref": null, "suggestion": null},
                                  // suggestion = 情报注入插座(二期 bid-quote 建议卡,约束5的接口预留)
  "from_addendum": false,
  "superseded_by": null
}
```
> 该 JSON 是持久产物:跨会话续作、二期资产库/生成/评分预测都消费它。Word 只是它的投影视图(codex steelman 采纳)。

**投标文件结构镜像 — structure.json**(覆盖**两卷**:格式章节若同时规定技术部结构,技术卷同样入镜像):
```json
{
  "node_id": "S-012",
  "volume": "commercial",           // commercial(商务卷) | technical(技术卷)
  "path": "投标文件格式/三、法定代表人身份证明",
  "slot_type": "image",              // text | table | image | format_check | group(纯章节容器)
  "required_format": {"desc": "加盖公章的身份证正反面扫描件", "table_spec": null},
                                    // table 槽:复刻列头/行列结构;format_check 槽:签字/盖章/份数/
                                    // 页码/目录等非内容格式义务——只能人工核验,报告单列"人核项"
  "linked_clause_ids": ["ZB-C-034"],
  "fill_status": "unfilled"          // unfilled | filled | needs_human_verify(槽位自有枚举——
                                    // 镜像槽不存在"偏离"概念;条款状态权威,槽位状态派生同步)
}
```
> "结构即合规":章节顺序/表格格式/图片位置全部来自招标文件,skill 只镜像+打槽位,不自创任何结构。技术卷在格式章节未规定结构处,才退回条款清单驱动组织(兜底序)。

**评分标尺 — rubric.json**(从评分细则表抽取,每项):
```json
{
  "rubric_id": "R-005",
  "item": "技术方案先进性",
  "max_score": 10,
  "scoring_method": "优=8-10 良=5-7 一般=1-4 无=0",   // 评分办法原文锚点
  "score_type": "subjective",      // objective(证书有无/参数满足=状态汇总) | subjective(LLM 评审)
                                  // | price(报价公式分,依赖竞对报价——mock 数据无法模拟,报告标"无法模拟")
  "linked_clause_ids": ["ZB-C-041"],
  "source_ref": {"page": 31, "section": "评分办法", "quote": "…"}
}
```
> rubric.json 由阶段2 的 LLM 循环从评分细则表抽取(extraction_prompt.md 子模板③);score_simulate.py 校验 Σmax_score 与评分办法声称总分一致,不一致→评分报告异常项并中止(extract.py 已在阶段2 前置拦截、确认门1 已列异常项,此处为纵深复检)。

**状态一致性三防线(D7,轻量版;完整 manifest 留二期多会话场景)**:
1. 外键校验:extract/merge/重灌每次装载三件套时校验 linked_clause_ids 存在且未 superseded(~5 行,悬挂引用→异常项,不静默);
2. 派生字段不入库:fill_status 等派生态渲染/重灌时现算,不落盘——拆掉双写分叉的根源;
3. 原子写盘:所有状态文件统一 临时文件+os.replace,防中断留半截文件。

**管线六阶段(两道人工确认门;阶段0-4 主线,阶段5 填写后可反复)**:
```
阶段0 输入受理   上传 N 份基础文件(招标文件/技术规范书/图纸/评分办法常为分卷)→
                分流:.docx=python-docx(zipfile+XML 兜底) / .pdf=pdfplumber /
                无文本层页=eai-flow-ocr(全文模式,需扩展端点,见 Open Questions);
                答疑/补遗标记为增量输入;clause_id 复合前缀按文件代号分配
阶段1 ingest    纯结构化解析→按章节切块,每块带 {source_file, 锚点, chunk_id} →
                sections.json;锚点按来源:docx=section+段落序,PDF/OCR=page+section;
                每张表(含行数)亦发稳定 table_id 并计入 sections.json——
                覆盖度防线(D5):阶段2 对每个 chunk_id/table_id 必须产出裁决
                ("0 条→门1 显式判空"或"N 条"),表行数由 ingest 端比对,防 pdfplumber
                吞表后静默漏检;
                定位"投标文件格式"类章节 → 只产出章节树骨架(槽位语义定型留给阶段2)
阶段2 extract   Agent 在上下文内跑分块提取循环,三类子任务共用一套循环纪律
                (提示词=extraction_prompt.md 三个子模板,每次一个 chunk,候选 JSON 落盘):
                ①条款提取→clauses.json;②格式章节槽位定型→structure.json
                (识别"此处为盖章扫描件"=image 槽/从散文复原表格规格等语义工作在此
                完成,ingest 只给章节树);③评分细则表→rubric.json;
                extract.py 做确定性校验:锚点必须存在于 sections.json、枚举合法、
                跨块去重、rubric Σmax_score=评分办法总分、chunk_id/table_id
                全量有裁决(无裁决 id 一律[待确认]进确认门1——零漏检是管线
                不变量,不是验收口号);分类判据来自
                classification.md(★/"实质性响应"/废标条款字样→mandatory;
                评分细则表→scoring;其余→normal)
                上下文纪律(防 Approach A 复发):读原文用 read_file 行区间,每块
                候选即刻落盘为 checkpoint,只保留摘要进上下文;超长文档分批,
                必要时经 task() 子代理分卷处理(注意 3 并发上限)
──── 确认门1(防上下文打爆):对话内只展示计数(强制N1/评分N2/普通N3)+异常项
      (强制待确认/未锚定/评分表降级项/rubric 总分不符/未裁决 chunk·table 显式判空);
      完整清单落盘为 markdown 工件
      (clause_id/原文引文/锚点/章节列),用户在对话里按 clause_id 改分类,
      Agent 回写 clauses.json;校验失败块保持[待确认]。
      本门同时锁定实体白名单:封面/投标人须知抽取的公司名/项目名/参数版本,
      用户增删后确认——供阶段4 实体 lint 消费────
阶段3 merge     补遗/答疑文件同样走0-2(到达即处理,不重开已过的确认门,合并 diff
                统一在下一次确认门/确认门2 呈现),合并算法分三级:
                ①章节锚点精确匹配→自动 ②相似度候选由 Agent 在上下文内产出
                (脚本不调 LLM,同阶段2 模式)→列给用户 ③平手→人工裁决;
                裁决结果交 merge_addenda.py 确定性落账;内容哈希台账(每份补遗
                hash+时间戳)保证幂等,重复合并直接跳过;
                新增条款入库(from_addendum=true)/修改条款旧项标 superseded_by/作废标废
阶段4 build     输出五件套(商务/技术双卷):
                ①商务部骨架:structure.json 渲染——镜像章节树,每槽位标注
                  类型/格式要求/待填内容提示(image 槽列出需用户提供的扫描件清单)
                ②技术部骨架:技术参数逐项(要求原文锚点→响应要点→证据引用→
                  满足状态→suggestion),条目标题嵌入 clause_id(如"2.3.1 响应[ZB-C-017]"
                  ——convert.py 链路不支持隐藏标记/HTML注释(仅粗体/斜体),
                  clause_id 入标题是阶段5 重灌唯一可存活的锚点载体,交付物中
                  保留不删);格式章节规定了技术卷结构的部分按镜像渲染
                ③偏离表(仅强制+偏离项)+覆盖率报表(清单总数/已响应/待确认/未分配)
                ④实体一致性 lint:实体白名单(确认门1 锁定)diff 全部 evidence_ref
                  与引用片段,上一项目残留→标[待核对];白名单由 LLM 抽取+人工确认,
                  lint 标注"LLM 辅助",不称确定性
                ⑤Word ×2 卷:markdown→markdown-to-docx(强制条款**加粗**——
                  convert.py 不支持高亮)。渲染边界如实声明:管道表格无法表达合并
                  单元格/列宽→此类表格槽标[待人工复刻]并入人核清单;图片不经 md
                  链路插入,而是生成扫描件清单+python-docx 后处理插占位图,终稿
                  人工替换;format_check 项(签字/盖章/份数/页码)全部人核,
                  不进确定性判定
──── 确认门2:①补遗合并 diff 表(新增/被替代/作废清单,逐项确认;含"新实体确认"列——
      补遗新增实体默认勾入实体白名单,人工可改,阶段4 lint 始终用最新白名单,
      防补遗后合法新实体被误报[待核对])②终稿复核清单
      (格式/资质/报价/承诺项+format_check 人核项必须人工签字,skill 不做最终承诺)────
阶段5 模拟评分  (终稿提交前必跑;可重跑,报告 version++ 留痕不覆盖历史——
                二期评分校准闭环消费历史版本)
                成稿两种形态,先对齐再评分:
                · 会话内填写态 = clauses.json/structure.json 当前状态(即时);
                · 团队回传 Word = 先经 uploads 自动转换(docx→md,既有链路),
                  score_simulate.py 对回传 md 做确定性锚点匹配,把各槽/条款实际
                  填充情况重灌进 clauses.json/structure.json——不重灌会出现
                  "客观项按旧状态计 0 分、主观项按新稿评高分"的自相矛盾;
                **重灌锚点契约**(锚点载体在 build_output 渲染时即埋定):
                · 商务卷锚点 = structure.json 树路径的标题链(章节标题=招标文件
                  规定结构,改标题本身即形式违规→标题天然稳定,无需额外标记);
                · 技术卷锚点 = 条目标题内嵌的 clause_id(阶段4②渲染时埋入);
                · 重灌输入文件必须显式指定(用户指定或线程内最新回传)——团队
                  多版回传并存时防"灌了旧版"状态漂移;
                · 匹配失败项标 needs_human_verify(重灌失败待人核)——既不计 0 分
                  也不静默通过,汇总进评分报告异常区;
                匹配器硬化规则(D6,四类失败全显式):
                · 同一锚点多命中(目录与正文同名标题/两卷共用小节名)→不取首个,
                  整项进异常区待人核(防静默灌错——比匹配失败更危险);
                · 匹配前文本归一化(去编号/空白/全半角)——防团队改样式/Word 自动
                  编号导致精确匹配雪崩进人核洪泛;
                · clause_id 在回传稿重复出现(Word 修订模式 docx→md 重复文本)→
                  异常区;
                · 重灌命中率低于阈值→整体降级为"人核覆盖率清单",不做部分计分
                  (匹配不可靠时退回人工模式,而非灌半套状态);
                重灌数据流(实现期落 score_simulate.py docstring):
                  回传.docx → uploads 自动转换 → 回传.md
                    → 商务卷: 标题链匹配 structure.json path
                    → 技术卷: clause_id 匹配 clauses.json
                    → 未匹配槽/条款 → needs_human_verify(报告异常区)
                    → 重灌后状态 → objective 汇总 + subjective LLM 评审;
                评分:
                · objective 项 → 确定性汇总(基于重灌后的清单状态——是汇总不是
                  验证,其可信度取决于状态维护)
                · price 项 → 标"无法模拟"(依赖竞对报价,现库为 mock)
                · subjective 项 → Agent 逐项 LLM 评审:评分办法原文为尺,证据
                  定位用 grep 检索回传 md/会话内骨架(仓库已验证模式),逐项
                  独立评审,给分+理由+失分点
                · score_simulate.py 汇总渲染 → 评分模拟报告:
                  逐项得分/满分/理由/失分原因 + 改进建议清单
                  (按 失分值×可改性 排序),主观分标注"模拟参考值"
```
脚本执行环境:本地沙箱(LocalSandboxProvider,`/mnt/skills/public/...` 形态,同 markdown-to-docx 先例)——文件可达上传区/线程目录;脚本不调 LLM(已启用技能的脚本无对话类 LLM 调用先例——脚本侧凭证先例仅 {image,video}-generation 媒体 API,见 Approach B;沙箱 env 策略默认剥离平台凭证;Agent 驱动的循环可审计、可中断),提取/评审循环由 Agent 在上下文内驱动。

**技术部证据填充(搭便车检索,用户补充后升级为双源)**:
1. **手动上传样例方案**(主源,V1 完整支持):用户把旧标书/样例方案/资质/参数表拖进线程(走既有上传→sandbox),填骨架阶段 SKILL.md 指示 Agent 对附件全文检索(`grep`/python 读文件)引用片段进 `evidence_ref`,零持久化基建。
2. **知识库查询**(按可达性分级):
   - **已可达(价值存疑)**:`knowledge-factory` MCP 已注册,Agent 可直接调 `kf_query_templates`/`kf_resolve_template`——但其语料是环评/水保/消防类报告模板,是否含投标方案模板未实测;V1 先调用一次探测,空手而归则此源如实降级为"不可用";
   - **当前不可达**:`knowledge` 扩展(RAGFlow client)存在但**无 MCP 接线**(mcpServers 列表无它)。RAGFlow 本身部署在用(v0.25.3),内容分级:表格(HTML chunk)=现成/图片(image_id 引用+取图端点,client 未封装)/公式(LaTeX,需入库时配置解析器,旧库无法事后补救)——**全文语料检索 V1 不承诺**,接线/取图封装/入库规范列为 Open Question 9,若落地则二期接入。

**知识库可达性(实测结论,2026-08-16)**:agent 侧"知识"今天只有 knowledge-factory(模板/合规向)真正可达;真正的文档语料检索(RAGFlow)无 agent 原语接线。设计据此如实分级,不虚设"从知识库查询"能力。

**SKILL.md 铁律**(移植 water-drainage 实证教训,逐条对应):
1. 条款数据的唯一来源 = `clauses.json`;严禁在 prose 里转写/改分类——改分类必须改文件。
2. 先跑通 ingest/extract 才允许谈清单;校验失败的块标 `[待确认]`,绝不绕过自提取。
3. 禁止"整篇方案生成器"脚本;商务部/技术部骨架由 build_output.py 从 clauses.json + structure.json 渲染;商务部章节结构**只镜像不自创**。
4. 全程写盘仅限:脚本产出的 artifacts + 最终 Word 落盘(每卷单次成文,共两次);禁止多次 append 拼接。
5. 耗时自检(分级阈值,不同阶段不同量级):脚本/Agent 提取循环=分钟级,确认门1 前超 ~5 分钟无 clauses.json 产出→偏轨停下;OCR 全文=百页量级十几分钟属正常(OCR 服务实测节奏),只设每 N 页心跳进度,不设一刀切死线。
6. 多轮承接锚点:每会话结束写 `project_snapshot.json`(当前招标文件/清单版本/待办/评分报告版本),防止跨会话漂移回"重新生成";评分报告 version++ 留痕,不覆盖。
7. **评分纪律(阶段5)**:模拟评分必须逐项引用评分办法原文锚点+成稿证据片段;无证据的响应按空缺计分(不为留印象给分);主观项一律标"模拟参考值",skill 不承诺与真实评审一致;改进建议必须落到具体 rubric_id 与缺失内容,不写空话。

**验收方法**(codex 建议采纳,经评审修正为可证伪形式):取一份客户真实(已完结)招标文件 + 老手当时的手工响应清单,跑提取对比。硬门槛 = **对老手清单召回 100%**(其条目全部命中)+ **增量项由老手裁决**(skill 多提取的、他漏掉的条目,逐条判定真伪)。"绝对零漏检"不可证(老手清单本身不是完整 oracle),以此双门槛替代。

**工作量估算**(按五脚本/双卷/rubric 范围重推,含 eng-review 新增的 D5 覆盖度防线/D6 匹配器硬化/D7 状态一致性三防线 ~75 行及测试):CC ~4-6 天——脚本 2.5-3 天(ingest+兜底路径/extract 校验+全量裁决/merge 台账+外键校验/build 双卷渲染+lint/score_simulate 重灌+匹配器硬化+汇总)、SKILL.md+分类/评分/抽取三套规则 1 天、样例联调+评分校验 1-2 天;评审注记:双卷表格复刻边界与 rubric 表格解析(OQ5)是最大的不确定项,若 rubric 降级为"整表图+人工确认"则上限再加。人力对照 ~3-4 周。

**二期路线(优先级序)**:
1. 资产库:旧标书/资质/业绩结构化入库(条款清单的 evidence_ref 指向库内资产)→ 整篇初稿生成解锁。
2. MCP 升舱:脚本管线吸收为 parse_tender/merge_addendum/build_skeleton 工具,清单持久化版本化。
3. 情报注入:bid-quote 真实库接入后,报价区间/友商构成建议卡注入响应骨架(suggestion 槽位消费)。
4. 格式合规自动化(暗标格式/目录/页码)——对接 output 扩展封面母版能力。
5. **评分校准闭环**:拿真实评审结果(中标/失标复盘)回灌,校准主观项模拟评分的系统性偏差——模拟分从"参考值"升格为"校准值"的前提。

## Success Criteria

- **硬门槛**(可证伪形式):真实招标文件上,对老手手工清单**召回 100%**;skill 的增量提取项(老手漏的)由老手逐条裁决,真阳 ≥90%。"绝对零漏检"不可证,以上述双门槛替代。
- **结构镜像保真**:渲染出的章节树与表格行列结构与招标文件要求逐项一致(人工抽查;合并单元格/列宽等 markdown 管道表达不了的部分以[待人工复刻]清单交付并计零遗漏——这是形式评审的生死线)。
- 每条条款可回溯原文位置(锚点抽查 100% 命中)。
- 补遗合并幂等(重复执行不产生重复条款)。
- **模拟评分闭环可用**:真实标书+两种成稿形态(会话内填写态/团队回传 Word 重灌后)各产出一次完整评分模拟报告(每 rubric 项有得分+理由+证据引用;price 项如实标"无法模拟");老手对失分点判断的认同率 ≥80%(不认同项记录并回改 scoring_prompt)。
- 行为指标:老手在 ≥1 次真实投标中使用;响应骨架被团队直接分发填写(而非重新手写)。
- 反指标:任何编造的资质/参数/承诺出现在输出中 = 该次交付失败。
