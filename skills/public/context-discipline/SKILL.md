# 上下文使用纪律（context-discipline）

## 原则

上下文窗口是稀缺资源。上下文中放的不是信息本身，是**获取信息的能力**——引用、路径、查询语句。信息本体躺在文件里。

## 四级出手顺序（成本递增，能前不后）

### 1. 即时加载（成本最低，默认选择）

- 需要时才读：上下文只保留文件路径、链接、表名/查询语句这类轻量引用，用 `read_file` / 检索工具现取，用完即弃
- 大文件先看目录或头部定位，再只读需要的段落（`read_file` 支持行区间）
- 不把整个文件内容粘进对话；不每轮复述已确认的长背景

### 2. 外化到文件

- 属于整个任务但不属于当前这一轮的信息（中间结果、长清单、数据表、过程草稿），写入 workspace 文件（`/mnt/user-data/workspace/` 下），上下文只留**结论 + 文件路径**
- 多轮任务配合 task-notes 技能维护 `TASK.md`（四节：当前目标/已做决定/已完成与改动/下一步）

### 3. 压缩重启（系统自动，你做准备工作）

- 上下文接近上限时平台自动做摘要压缩，无需你触发
- 你的责任：压缩发生前 `TASK.md` 是新的、关键工作文件路径已在对话或笔记中——压缩摘要会保留路径，压缩后循路径重读恢复细节
- 压缩后恢复：先读 `TASK.md`，再按需读笔记中列出的工作文件

### 4. 拆子 Agent（成本最高，最后手段）

- 仅当子任务上下文互相污染、或需要干净窗口深挖时才 `task()` 委派——拆分本身有编排开销
- 委派 prompt 中明确要求对方**只返回四样**：结论、关键证据、风险点、下一步建议
- 不要索要或接受子 Agent 的完整工作过程（几十次工具调用记录）——隔离做了又倒回来就白做了
- 简单子任务不拆：自己几步做完的别委派

## 反模式清单

- 把整个文件内容粘进对话
- 每轮重复已确认的长背景信息
- 预读"可能用得上"的大文件
- 简单子任务也拆 Agent
- 委派时让对方汇报全部过程痕迹
