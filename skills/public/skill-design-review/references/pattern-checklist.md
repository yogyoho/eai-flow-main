# Skill 设计模式审查清单

审查一个 `SKILL.md` 时，对照以下 5 种设计模式逐条检查。

---

## 模式 1：Tool Wrapper（工具封装）

**本质：** 给 agent 提供某个特定库/框架的按需知识。不硬编码到 system prompt，而是打包成 skill 按需加载。

**检查项：**

| # | 检查点 | 严重度 |
|---|-------|:----:|
| 1.1 | 技能描述中是否声明了触发关键词（库名/框架名/技术名）？ | error |
| 1.2 | 是否指示 agent 在特定条件下加载 `references/` 中的参考文件？ | error |
| 1.3 | 参考文件中的规则是否具体、可执行（不是泛泛的"遵循最佳实践"）？ | warning |
| 1.4 | 是否区分了"审查代码"和"编写代码"两种场景的不同指令？ | info |
| 1.5 | 知识是否模块化（每个 reference 文件聚焦一个主题）？ | info |

**适用场景：** 团队编码规范、框架 API 指南、领域术语词典

---

## 模式 2：Generator（生成器）

**本质：** 强制执行一致的输出结构。模板 + 风格指南 → 填充 → 输出。

**检查项：**

| # | 检查点 | 严重度 |
|---|-------|:----:|
| 2.1 | 模板文件是否存在于 `assets/` 或 `references/` 目录？ | error |
| 2.2 | 是否要求 agent 加载模板后再生成内容？ | error |
| 2.3 | 模板中每个章节是否都有明确的填充指引？ | warning |
| 2.4 | 是否要求 agent 在内容缺失时询问用户而非编造？ | error |
| 2.5 | 是否有风格指南规定语气、格式、术语？ | info |
| 2.6 | 输出检查：是否要求模板中每个章节都必须出现在输出中？ | warning |

**适用场景：** 报告生成、标准化文档、项目脚手架

---

## 模式 3：Reviewer（审查器）

**本质：** 将"检查什么"（检查清单）与"怎么检查"（审查协议）分离。

**检查项：**

| # | 检查点 | 严重度 |
|---|-------|:----:|
| 3.1 | 检查清单是否独立存放在 `references/` 中（不是嵌在 SKILL.md 里）？ | error |
| 3.2 | 每项检查是否有明确的严重度分级（如 error/warning/info）？ | error |
| 3.3 | 审查协议是否要求输出结构化报告（摘要→发现→评分→建议）？ | warning |
| 3.4 | 每条违规是否要求解释"为什么是问题"而不只是"哪里不对"？ | warning |
| 3.5 | 是否要求给出具体的修正建议（不泛泛的"改进代码质量"）？ | error |
| 3.6 | 检查清单是否模块化（换一份清单=完全不同的审查）？ | info |

**适用场景：** 代码审查、安全检查、设计审查、合规检查

---

## 模式 4：Inversion（反转询问）

**本质：** Agent 作为访谈者，先收集信息，信息不全不解问题。

**检查项：**

| # | 检查点 | 严重度 |
|---|-------|:----:|
| 4.1 | 是否有显式的门禁指令（"在所有阶段完成前不要开始构建/编码"）？ | error |
| 4.2 | 是否分阶段？每阶段的问题是否有明确的顺序？ | error |
| 4.3 | 是否要求一次只问一个问题？ | warning |
| 4.4 | 是否要求等待用户回答后再进入下一步？ | error |
| 4.5 | 最终输出前是否有用户确认步骤？ | error |

**适用场景：** 需求收集、项目规划、故障诊断

---

## 模式 5：Pipeline（流水线）

**本质：** 强制严格的顺序工作流，每步有检查点，禁止跳步。

**检查项：**

| # | 检查点 | 严重度 |
|---|-------|:----:|
| 5.1 | 步骤是否有明确的数字编号（第 1 步、第 2 步...）？ | error |
| 5.2 | 是否有显式的禁止跳步指令？ | error |
| 5.3 | 关键节点是否有硬检查点（用户确认、验证通过）才能进入下一步？ | error |
| 5.4 | 每步是否声明了所需的输入文件和输出产物？ | warning |
| 5.5 | 失败处理：某步失败时是否有明确的回退/停止策略？ | warning |
| 5.6 | 是否利用了 `assets/` 和 `references/` 的分步加载来保持上下文窗口干净？ | info |

**适用场景：** 文档生成流水线、多步骤数据处理、报告生成+审核+导出

---

## 通用检查项

| # | 检查点 | 严重度 |
|---|-------|:----:|
| G.1 | YAML frontmatter 是否包含 name 和 description？ | error |
| G.2 | description 是否写明触发场景（"当用户请求 XXX 时使用"）？ | error |
| G.3 | 指令是否具体可执行（不是"你应该聪明地处理"这类模糊表述）？ | error |
| G.4 | 是否有不必要的工具调用说明（应交给 agent 自行判断）？ | info |
| G.5 | 是否与其他 skill 有清晰的路由规则（什么情况下用A不用B）？ | warning |
| G.6 | 是否正确使用了 `references/` 和 `assets/` 目录？（大段知识在 reference 里，不在 SKILL.md 里） | warning |
