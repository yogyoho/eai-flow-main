三个方案：直接映射"我的文档"到线程 outputs/

共同前提：项目文件夹保持不变。个人文档的收藏/分享保留。

A

新 API + 轻量元数据表（推荐）

全新 GET /docmgr/personal-outputs 端点直接扫描 filesystem 返回线程文件夹+文件列表。收藏/分享存到一个新的轻量表 personal_doc_meta(user_id, thread_id, rel_path, is_starred, is_shared)。旧的个人 AIDocument/Folder 记录不再使用。同步链路 sync_thread_files 对个人 scope 停用。

优点

  • 数据路径干净：outputs → API → 前端，无 DB 中间层
  • 文件写完立即可见（无同步延迟、无时序问题）
  • 不会误入 uploads/workspace（只看 outputs）
  • 收藏/分享专用表，不影响文档主体逻辑
  • 旧 DB 数据可以逐步清理

缺点

  • 需要新增 API + 一张表
  • 旧个人文档的收藏/分享状态需要迁移
B

复用 AIDocument 做轻量索引（最小改动）

保留个人 AIDocument 表但只存最少字段（file_ref_path, thread_id, user_id, is_starred, is_shared），不再写 Folder。前端新 API 直接查 AIDocument 按 thread_id 聚合显示，不再走 folder tree。同步链路保留但只同步 outputs/。

优点

  • 改动最小，复用现有表结构
  • 收藏/分享字段已存在
  • 现有数据的收藏/分享不丢失
  • 后端 sync_thread_files 改一下 skip 逻辑即可

缺点

  • AIDocument 仍在中间——还是没有真正"直接映射"
  • 同步延迟问题仍存在（仍需 sync 触发）
  • Folder 表对个人 scope 变成僵尸数据
C

纯文件系统（无 DB）

完全跳过 DB。前端调 artifacts API 列出 outputs/ 下文件。收藏/分享用文件系统 JSON 存储（如 .deer-flow/meta/{thread_id}.json）。所有元数据（star, share）与文件在同一位置。

优点

  • 最彻底的直接映射，零 DB 依赖
  • 元数据跟随文件，备份/迁移简单
  • 个人与项目完全解耦

缺点

  • 文件系统 JSON 读写并发不友好
  • 搜索/过滤效率低（无法用 SQL）
  • 分享功能需要额外设计（文件系统无网络语义）
  • 改动最大，出问题调试难
