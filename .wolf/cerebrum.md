## Key Learnings

- **Project:** eai-flow-main

- **Database session providers:** Always reuse a shared engine pool. Never create+dispose engines per request — the overhead is catastrophic. Use `pool_pre_ping=True` instead of `SELECT 1` validation on every request.
- **Nginx upstream keepalive:** Always add `keepalive N` to upstream blocks and set `proxy_set_header Connection ''` on location blocks to reuse TCP connections to backend.
- **MCP skill tool filtering:** Skills with `allowed-tools` declarations in SKILL.md cause `filter_tools_by_skill_allowed_tools()` to strip ALL tools not in the allowed list, including MCP tools. If no skills are enabled, the filter returns None (allow-all). Disabled/renamed skills don't count.
- **allowed-tools is a GLOBAL agent whitelist, not per-active-skill (2026-06-18, bug-186):** `skills/tool_policy.py::allowed_tool_names_for_skills()` takes the UNION of `allowed-tools` across ALL enabled skills, and "once any skill declares the field, skills WITHOUT it contribute nothing". So ONE enabled skill declaring `allowed-tools` (e.g. `geological-report` → 6 built-in tools) becomes the ENTIRE agent's tool whitelist, stripping every MCP tool (`knowledge-factory_kf_*`, `word-document-server_*`, etc.) and every other skill's needed tools — regardless of which skill is active. Symptom: knowledge-factory-dependent skills (`fire-protection-report-v2`, `coal-eia-report`) "can't see" the MCP tool and silently fall back to static markdown; the model even says "I need tool_search to find MCP tools" (it literally doesn't have them). Diagnose by replicating `agent.py`'s assembly: `get_available_tools(...)→filter_tools_by_skill_allowed_tools(...)→_assemble_deferred(...)` and checking if the target tool survives (count dropped 81→5 = smoking gun). Fix (skill-layer, no core code): remove `allowed-tools` from the offending skill's SKILL.md. Proper fix (core, deferred per "don't change core code"): scope `allowed-tools` to the active skill only. Verify the fix: tool count returns to 81 and the agent calls the MCP (gateway log: `Externalized <server>_<tool> output (N chars)`).
- **word-document-server MCP intentionally disabled (2026-06-18, user decision):** It's OFF in extensions_config.json by the user's choice, NOT a regression. It exposes 54 .docx-crafting tools (headings/tables/footnotes/cell-merge/PDF/protection) — none used by current report skills, which route Markdown → docmgr → Word export via `output/generator.py` (python-docx), independent of this MCP. Keeping it off drops the agent toolset ~81→27 (less tool-selection noise, better instruction-following). Only re-enable if a future skill needs the agent to directly author/fine-edit .docx without the docmgr middleman. DON'T flag the "missing 54 tools" as a bug — it's intentional.

Turbopack tries source resolution and ignores the `exports` map, resulting in undefined imports at runtime. ## Key Learnings (2026-06-30)
- **内网离线部署规范路径** = `deploy/offline/` + `scripts/offline-export.sh` 产出的 `install.sh` 包(eai-prod/端口4026, GUIDE v2.0 已验证)。`docker/docker-compose-offline.yaml`(eai-docker/12026)是已废弃旧方案,已删除。`deploy/offline/deploy.sh` 是 broken 的备入口(CORE_FILES bug),install.sh 才是主路径。
