## Key Learnings

- **globals.css 的 EAI-CUSTOM 修改会被 upstream sync 覆盖——涉上游文件的修复必须放独立 CSS 文件 (2026-07-23, bug-264, Do-Not-Repeat):** 上次给 `var(--border)` 加 fallback 的 6 处修改全被 sync commit `8626bbba`/`7467163f` 覆盖（恢复到 bytedance/main）。`/* EAI-CUSTOM */` 注释是 code-review gate（没加=打回），不是自动 sync 保护——sync 按 diff 对齐上游，不管注释。**铁律：任何涉 `globals.css` 这类上游维护文件的样式修复，一律写到独立 CSS 文件（如 `eai-overrides.css`），在 `layout.tsx` 中于 globals.css 之后 import，靠源序优先覆盖。** 独立文件不在上游 tree 内 → sync 永不会碰。同一原则适用：`global-error.tsx`、`not-found.tsx`、`next.config.js` 这类本地有改动但上游也维护的文件。

- **`var(--border)` 无 fallback = 全局偶发黑边框的系统性根因，别再 whack-a-mole 加 `!important` (2026-07-22, bug-259, Do-Not-Repeat):** Tailwind v4 `@layer base { * { border-color: var(--border) } }` 是 shadcn 约定。当 `--border` 在 CSS 加载竞态期（FOUC / next-themes 预水合 / 流式或懒加载组件 CSS chunk 未到）短暂未解析，`var(--border)` invalid-at-computed-time → border-color 回退初始值 `currentColor`（≈文字色≈近黑），带 border-width 的元素即显黑边框。本项目 globals.css:607-627 已对 react-resizable-panels / react-flow 用 `border-color: var(--border) !important` 逐个打补丁——那是症状，新组件（buttons / task panel / artifacts / ProseMirror table）会继续复现。**正确治法：给每个 `var(--border)` 用法加 fallback**（`rgba(130,130,130,0.25)` 淡中性灰，明暗都柔和）。改 base `*` 时要从 `@apply border-border` 改成裸 `border-color: var(--border, ...)`，否则 `@apply` 生成的无 fallback 声明会按源序覆盖掉 fallback。判定方法：看到偶发黑边框先 grep `var(--border)` / `var(--ring)` 等主题变量无 fallback 的用法，别急着给单个组件加 `!important`。

- **rename 任何 export 符号必须全量 `grep -rn` 整个 `src/`，不能只搜"看起来相关"的目录 (2026-07-21, bug-174 渲染层 followup, Do-Not-Repeat):** port PR#2411 把 `rehypeSplitWordsIntoSpans`→`rehypeFadeInBlocks` 时，我只 grep 了 `components/workspace/messages/`，漏掉 `core/streamdown/plugins.ts`(它 import 该符号加进 streamdown 的 rehype 链)。结果 Turbopack 编译报 `Export rehypeSplitWordsIntoSpans doesn't exist`。铁律：rename export 后必须 `grep -rn "旧名" frontend/src` 确认零残留，尤其 `core/streamdown/plugins.ts`、`core/streamdown/components.tsx` 这类共享 plugin/config 文件——它们被多个组件间接引用(import trace 会经 artifacts/settings/memory-settings 等多处)。补丁 commit 16659a02。

- **LangGraph SDK useStream 的 trackStreamMode 会把 `values` 全量快照偷偷加回 streamMode——e684a369 的"submit 去 values"无效 (2026-07-20, bug-174, Do-Not-Repeat):** `useStream` 返回对象有 `get values()`/`get messages()`/`getMessagesMetadata()` 等 getter,每次访问都 `trackStreamMode("values")` 把 mode 累积进持久 ref(`stream.lgp.js:132-135,394,431,443`)。submit 时 `unique([submitOptions.streamMode, trackStreamModeRef.current, callbackStreamMode])` 合并(`:264-268`)。前端渲染必访问 thread.values/messages → values 必被加回 → 实际 SSE 含 values 全量消息历史快照。`callbackStreamMode` 还因 onLangChainEvent/onCustomEvent/onUpdateEvent 加回 events/custom/updates。**判定方法**:看到 `e684a369`-类"submit 显式传 streamMode 去 values"的优化时,必须检查是否被 trackStreamMode/callbackStreamMode 合并回——submit 传值不等于实际请求值。真正去 values 只能:①后端 StreamBridge 拦截(values events 不发或仅 run 结束发);②patch SDK(不可持续);③前端不访问 thread.values。这是流式长会话卡顿的层 0 根因,比渲染层(每 chunk 全量 re-parse)更治本。相关 [[bug-172]] [[bug-173]] 同属 chat 渲染性能。

- **CSS `contain: paint` 会裁剪溢出的 absolute 后代——本地性能优化吃过的亏 (2026-07-20, bug-173, Do-Not-Repeat):** commit 5c21578a 给 `message-list.tsx` 的消息 group div 加了 `cv-auto contain-layout`(globals.css 定义为 `content-visibility:auto` + `contain:layout style paint`)。`contain: paint` 按规范把后代裁剪到元素边界(含 absolute 后代),而 human 消息复制按钮工具栏 `MessageToolbar` 定位是 `absolute -bottom-9`(message-list-item.tsx:174, 消息下方36px),溢出 group 底部 → 被裁剪 → 复制按钮消失。上游 `bytedance/main` **从未**有 `cv-auto/contain-layout`(grep 空),上游正常。**铁律:给容器加 `contain: paint`(或 `content-visibility:auto`,它隐含 paint containment)前,必须确认没有 `absolute` 子元素溢出该容器边界**——尤其是 hover 工具栏、tooltip、dropdown 这类常溢出父容器的浮层。修复=移除该类回到上游(代价是失去 content-visibility 滚动性能)。相关 [[bug-172]] 同属 message-list 性能优化的边界副作用。受 [[no-core-code-changes]]/上游一致约束,改前确认。

- **Tailwind v4 color-token override for scoped theming (2026-06-22, sci-fi page):** Tailwind v4 emits color utilities as `color: var(--color-blue-400)` (real CSS vars from `@theme`). To make a self-contained themed component (e.g. `.cyber-root`) flip accent colors per app theme WITHOUT editing every class, re-define the tokens under a scoped selector: `.light .cyber-root { --color-blue-400: #2563eb; --color-purple-400: #9333ea; … }`. Every `text-blue-400`/`text-purple-400` inside that subtree then resolves to the darkened shade automatically. `.light .cyber-root` (specificity 0,2,0) beats the `:root` theme definition (0,1,0). - **MCP skill tool filtering:** Skills with `allowed-tools` declarations in SKILL.md cause `filter_tools_by_skill_allowed_tools()` to strip ALL tools not in the allowed list, including MCP tools. If no skills are enabled, the filter returns None (allow-all). Disabled/renamed skills don't count.

So ONE enabled skill declaring `allowed-tools` (e.g. `geological-report` → 6 built-in tools) becomes the ENTIRE agent's tool whitelist, stripping every MCP tool (`knowledge-factory_kf_*`, `word-document-server_*`, etc.) and every other skill's needed tools — regardless of which skill is active. - [2026-05-28] Chose BlockNote over Tiptap for the collab editor. BlockNote v0.51 provides native Yjs collaboration support (fragment + provider + user + showCursorLabels), Notion-style block editing, and built-in markdown import/export (blocksToMarkdownLossy, tryParseMarkdownToBlocks). - **Collab seeding flow:** When a document is first opened in the BlockNote collab editor, the Hocuspocus server's `onLoadDocument` loads from `collab_documents.yjs_doc`. If no entry exists, it sets `pendingMarkdown` in Yjs metadata (`_collabMeta`). The client's `BlockNoteEditor.tsx` reads this metadata, seeds from the markdown using `tryParseMarkdownToBlocks()`, then clears the flag. This ensures content is always seeded from the correct source (`ai_documents.content` or file_ref file content).
- **BlockNote `tryParseMarkdownToBlocks` limitations:** BlockNote's built-in markdown parser has limited support for complex markdown (tables, nested lists, mixed Chinese/English). For complex technical documents, the parsed blocks may differ from the original markdown structure.
- **Two-storage system pattern:** The collab system has two storage tables: `ai_documents.content` (original markdown) and `collab_documents.yjs_doc` (Yjs binary). - **ExportDocxDialog integration gap:** When creating new dialog components, always complete the full integration chain: (1) create the component, (2) import it in the parent, (3) add state to control open/close, (4) wire the trigger to set state, (5) render the component in JSX. ExportDocxDialog was written but steps 2-5 were never done, so clicking "Word 文档" just did a direct blob download.
- **Backend docmgr export endpoint was missing:** The frontend called `GET /docmgr/documents/{id}/export?format=md|docx` but no such route existed in `backend/app/extensions/docmgr/routers.py`. The `generate_docx` function lives in `output/generator.py`. Had to create both GET (simple export) and POST (with layout template) endpoints.
